# Changelog

All notable changes to Arnotes are documented in this file.

## Unreleased

- **The instance's name and icon are set by the instance admin.** Under **Settings**, **Branding** sets the name (at most 40 characters) and the icon (a square PNG of at least 512 by 512 pixels, or an SVG without scripts). **Reset to default** brings back "Taskmanager" and the built-in icons. The tab, the sidebar logo and the page titles show them on the next load. The help page **Name and icon of the instance** explains it. Stored in the new `instance_settings` table (one row); no rebuild. The PWA manifest and the emails and MCP texts still show the built-in name for now.

- **Extra email addresses.** An account can have more than one address. Add one under **Settings** → **Security**; a confirmation link is mailed to it and must be opened while signed in to the account. Each extra address needs two-factor or a passkey on the account, and while one exists those cannot be turned off or the last passkey removed. An extra address signs in with the account's password and receives invitations once confirmed. Help page **Extra email addresses**, `app/components/ExtraEmailsPanel.vue`, `app/pages/confirm-email/[token].vue`, `tests/extra-emails.test.ts`.
- **The office view on a crew's board.** A board a crew works on has an **Office** tab, next to **Board**, that opens the crew's office at `/office/<boardId>`. Other boards have no such tab, and a customer's contact never sees it. The office's board name links back to the board, and so does its arrow. New help page "The office view", `isCrewBoard` in `server/utils/officeCast.ts` (the board payload's `crewBoard` flag), `tests/office-crew-board.test.ts`.
- **The office without WebGL.** A browser that cannot start WebGL no longer breaks the office page. It keeps the header, the board name and the link back, and says "This browser cannot show the 3D office." where the room would be. `openOfficeScene` in `app/office/openScene.ts`, `tests/office-webgl-fallback.test.ts`.
- **A crew can be given any other board of its own organisation.** A board in the crew's own team used to be refused. Now only the crew's own work board and the crew board it keeps are refused, with the same message; every other board of the team takes the crew. Tests in `tests/crew-own-organisation.test.ts` and `tests/crew-boards.test.ts`.
- **Replace an API key that Claude Code already has.** The copy box after a new key in **Settings** → **API keys & MCP** now offers an **update command**: it sets the new key, removes the existing `taskmanager` server and adds it again, in one paste. It works without an existing server too. **Connect an AI agent** and **Sprocket** say where `TASKMANAGER_API_KEY` must live (the shell profile, `~/.zshrc` or `~/.bashrc`, or an app's own environment settings) and that a new terminal is needed. The help page **Connect Claude Code to your boards** gets a step for the profile, a section on replacing a key, and the causes of `401 Invalid or missing API key` and `already exists in user config`. Shared in `app/utils/agentSetup.ts`, `tests/agent-setup.test.ts`.
- **The crew home folder is asked for once.** The commands a crew page or **Give a board a crew** copies start with `CREW_HOME`, which used to be a guess (`~/crew-home/<crew>`). The page now shows a **Crew home folder** field, prefilled with that guess, and this browser remembers the folder per crew; **Change** corrects it. Every copied command for that crew uses it. Nothing is sent to the server, and a browser that blocks storage keeps the guess. `app/utils/crewHome.ts`, `app/components/CrewHomeField.vue`, `tests/crew-home.test.ts`
- **A note when you decline a guest request.** Pressing **Decline** on a manager guest's request, in the Inbox or in the Share dialog, now opens a box for an optional note (up to 300 characters) that goes to the manager guest with the decision. The API already took the note; the app had no field for it.
- **Email addresses are private unless their owner shares them.** A new setting, **Who can see my email address** in **Settings**, is a slider with five steps: **Only me** (the default), **Managers**, **Team members**, **Guests** and **Everyone**. Every list that showed other people's addresses now applies it: a team's Members page, a board's people, members and assignee lists, the Share dialog's guests, the person card and profile, the owner on a team key and a customer's contacts. Where it hides an address the row shows the name alone. Before, any team member saw every teammate's address, and a board's staff saw each other's. The Better Auth team member list is scrubbed on the way out, so the Members page cannot be used to read them either. Not covered: an address typed on an invitation, which is listed to those who manage invitations. The instance admin's **Accounts on this instance** window is masked too: it shows each account's name and organisations, and typing a complete address finds that one account. New help page \"Who can see your email address\", `tests/email-privacy.test.ts`.
- **Resend an invitation.** A **Resend** button on open team and board-guest invitations makes a fresh link, valid for another 14 days, and the old one stops working at once. It is mailed when the instance can send mail and shown once otherwise. Owners and project admins may resend any open invitation, team admins and manager guests only their own. This replaces "withdraw it and invite again" for a lost link, and the approval notice to a manager guest now says to use Resend.
- **Team and board invitations are bound to the invited address.** On a closed instance a link no longer lets anyone create an account with any address: the new account must have the invited address (typed again by hand, or reported as verified by Google, GitHub, Discord or single sign-on), and any other address is refused with "Sign-up is closed here". The invitation page no longer shows the invited address, no longer reads the session until you press a button, and offers **Sign out** when the wrong account is signed in. The error for a wrong account no longer names the address either. An existing account still accepts only while signed in with the invited address. Customer links are unchanged. Aliases (extra addresses on an account) do not exist yet.
- **Who may withdraw a team invitation.** An owner may withdraw or replace any open invitation. An admin only the ones they sent, and the **Withdraw** button is hidden on the others. An admin can no longer replace an owner's open invitation by inviting the same address again.
- **Help pages for sharing and people.** New pages: "Invite people to a team by email", "Share a board with guests", "Invite people as a manager guest" (for guests with the customer view) and "Person card and profiles". The pages on the join code, members and roles, sign-in, the public link, teams, the workspace and shared boards now agree with them. The invite form, the Share dialog and the profile page carry a `?` hint that links to the matching page, and the role hints on the team page now mention inviting.
- **The skill on "Connect an AI agent" is generated.** The page kept its own hand-written copy of the agent skill, which had no timers, rules, goals, GitHub, help or inbox tools. It now shows `/api/settings/skill`, the same text the download gives, built from the tool registry. In that skill `start_timer` and `stop_timer` now sit under Time instead of Other, and the help tools have a Help group. New `tests/agent-skill.test.ts` fails when a tool has no group.
- **Boss's instructions: `Ready for live` and `Done`.** After a merge Boss moves a task to `Ready for live`, which hands the work to the Owner, and to `Done` once the Owner has taken it live or accepted it and nothing is left open for the crew (`crewBossSkill.ts`)
- **Boss starts only Pia.** The crew setup page and Boss's instructions (`crewBossSkill.ts`) now say that Boss starts the project manager in a session of her own and that she starts the workers and reviewers herself. The Boss window's message no longer launches the workers. No server or schema change
- **Crew person keys renamed: `pm` is `pia`, `nitpicker` is `nina`.** An existing crew is moved when the server starts, the same way as the earlier rename: account addresses (`<slug>-pm@crew.invalid` becomes `<slug>-pia@crew.invalid`, forks included), the names of the accounts' keys and the `crew_board_members.person_key` rows. The places that send an event to the crew's project manager (moves, unblocked tasks, GitHub events, failed deliveries and who may retry them) now look for the key `pia`. An address that is taken is left alone, and a second run moves nothing. No schema change. See `crew/CHANGELOG.md` for the kit
- **Quincy, QA, joins the crew.** A new crew has one more team member, Quincy Average (key `quincy`), and a board fork gets one for its board too. A crew made before gets him on its next rotate (`rotate: true`); a fork made before has none until it is forked again. The crew setup page names him in the messages it hands to Boss and the kit. The kit documents now describe the review gates (see `crew/CHANGELOG.md`)
- **No test may fail.** The test suite passes with 0 failures. A test that needs a dev server, a browser, `python3` or the crew kit's `node_modules` skips and states why. The dev server is found without assuming port 3000: `TEST_BASE_URL`, or the test's own variable, or the `nuxt dev` of the checkout (`.nuxt/nuxt.lock`), in `tests/helpers/testBase.ts`. `npm test` and `npm run test:crew` run the two suites. Cato's text (`crewBossSkill.ts`) says what he does with a task tagged `test failing`
- **Crew person keys renamed.** The crew's workers `w1` to `w4` are now `wren`, `wick`, `wynn` and `wade`, and the usability tester `pietje` is `usher`. A crew that already exists is moved when the server starts: the account addresses (`<slug>-w1@crew.invalid` becomes `<slug>-wren@crew.invalid`, forks included), the names of the accounts' keys and the `crew_board_members.person_key` rows. An address that is taken is left alone, and a second run moves nothing. No schema change. The kit moves an old crew home the same way (see `crew/CHANGELOG.md`)
- **A mention is kept in the inbox.** A comment that names someone with `@name` or `@first-name` now leaves a `mention` notification for each person on the board it names, instead of reaching only an agent that happened to be listening. It replaces the plain comment notice for that person, follows the same audience rule (an internal comment never reaches a customer's contact) and is sent by mail and push like the other notifications. Someone who is not on the board is not told, whatever their name. New notification type `mention`, no schema change
- **`start_timer` and `stop_timer` for agents.** An agent starts its person's timer on a task and stops it, instead of working out a duration for `log_time`. Starting a timer stops and logs the one that was running; stopping takes an optional note and logs at least one minute. They need the `boards:write` scope and appear in the agent audit
- **A team page at `/team`.** **Team** in the workspace menu opens it, in place of the old settings dialog. It has General (name, join code, leave or delete), Members, Customers and Board defaults, and for owners and admins Keys. Create and join stay as dialogs
- **Board defaults.** An owner or admin sets the columns a new board of the team starts with (up to 12, in order); boards that exist keep theirs, and an empty list puts back Backlog, To do, Verify, Done. New `team_settings` table, and `GET`/`PUT /api/teams/:id/settings`
- **Keys limited to one board or one customer.** An owner or admin makes a team key that reaches only one customer's boards or one board (`api_keys.customer_id`, `api_keys.project_id`; at most one of the two, and it must belong to the team). The board list, every tool that resolves a board, the owner's time across boards and the agent event stream are all cut to that reach, and the key is not given the tools that work across the whole team (goals, portfolios, `create_board`, the inbox). A key goes when its board or customer is deleted. The team's keys are listed under Keys on `/team`, with who owns them and when they were last used, and any of them can be revoked there: `GET`/`POST /api/teams/:id/keys`, `DELETE /api/teams/:id/keys/:keyId`

- **Team rules.** An owner or admin writes an if-this-then-that rule once under **Rules** on `/team`, and it runs on every board of the team, before the board's own rules. Any member can read them and their run log. A rule is chosen per rule as **by name** (columns written as names such as "Done", people picked from the team; a board with no column of that name skips the rule) or **column-free** (nothing that needs a column or a particular person, so it fits every board). The rule builder and its kind tables are shared with the board rule builder (`app/utils/ruleKinds.ts`). Only the team's owner can let a team rule set a task's visibility. New `team_rules` and `team_rule_runs` tables, and `GET`/`POST /api/teams/:id/rules`, `PUT`/`DELETE /api/teams/:id/rules/:ruleId`, `GET /api/teams/:id/rules/:ruleId/runs`

- **Give a board a crew.** An owner or admin of a team gives one of its boards a crew from **Crews** on `/team`, or from **Give it a crew** in the board's menu in the sidebar, and only with a crew they made themselves. That makes a shadow board in the crew's own team, linked to the real board (new `crew_boards` table), so every project the crew works on has its own crew context. Taking the crew off drops the link and archives the shadow board. The list shows who works on which board; a member of the crew's team opens its board from there with full access, and everyone else on the real board's team opens it read-only (a banner says so, and the server refuses every change, file downloads included). A customer never sees it. A team key reads the shadow boards of its team's boards through the read tools too. `GET`/`POST /api/teams/:id/crews`, `DELETE /api/teams/:id/crews/:linkId`
- **A crew reads its real board and never writes to it.** A crew account's key can, through the read tools only (`get_board`, `list_boards`, `get_task`, `search_tasks`, `list_task_labels`, `list_status_updates`, `list_messages`, `list_fields`), read the real boards its crew was given, every task on them. Every other tool, among them everything that writes and the reads of secrets and rules, does not find those boards at all. A key limited to one shadow board reads only the real board that shadow is linked to. Whoever runs the crew carries the results over

- **Fork a crew for a board.** On a board's crew link in **Crews** on `/team`, the owner or admin who attached the crew presses **Fork the crew for this board**. Each working member (the PM, four workers, the usability tester and the code quality reviewer) gets an account of its own, named for the board (agent type `internal-tools-wren`) and a member of the crew's team, with a key limited to exactly that board's shadow board. The keys are shown once, with a download of `forks-<crew>-<board>.json` that also holds each password. **New keys** replaces them, **Remove the forks** deletes the accounts, and taking the crew off the board removes them too. The crew's own rotate and status leave forks alone, since a rotate would hand out keys for the whole crew team and undo the limit; disabling the crew cuts them off with the rest. `POST`/`DELETE /api/teams/:id/crews/:linkId/fork`, new `crew_board_members` table

- **Help, tutorials and hints, written to the reader's permissions.** The help pages live in `docs/` as Markdown (concepts, how-tos and tutorials for boards and tasks, your workspace and time, teams and customers, rules, crews, AI agents and Sprocket, the GitHub integration and running the instance) and are bundled into the server build. The **Help** item in the account menu opens `/help`, with a start page, search and the pages grouped by topic. A small **?** hint next to a feature (Crews, Rules, Keys, Customers, Board defaults, the Timesheet, Sprocket, Connect an AI agent) explains it in a sentence and links to the page, and leaves the link out when the person may not open that page. Every page and every section of a page names what it needs (`staff`, `customer`, `team-admin`, `team-owner`, `instance-admin`, `write`, `secrets`, `crews`), and the server cuts what a person gets to what they may do: not listed, not found by a search, not readable, and answered as missing so a title is not given away. A browser session and an API key are cut the same way, and a key holds what its person holds, less what its permissions leave out. `GET /api/help` (with `?q=` to search) and `GET /api/help/:slug`; `docs/README.md` says how to write a page, and `tests/help-docs-content.test.ts` checks every page's front matter and links
- **Sprocket finds help, and stays inside its person's permissions.** `search_help` and `read_help` are in both ways Sprocket can answer (MCP tools for Claude Code and any agent, chat tools for OpenRouter), and its prompts tell it to look a "how do I" question up before answering, and to say so when something is not available to the person. The help is cut to the asker's permissions as above. Sprocket in Claude Code mode can only be run as a key of the person who asks (a test pins this), with Claude Code's own tools switched off, so it never reaches more than that key does
- **Give a board a crew, step by step.** **Step by step** in Crews on `/team`, and **Give it a crew** in a board's menu (which now opens it with the board picked), walk through four steps: pick the board and crew, fork the members or not, hand the keys over, check it. The keys step stays shut until the file is downloaded or the person says they copied the keys, since they are shown once
- **The crew kit takes forks.** `crew/init.mjs --forks <file>` stores the file from **Fork the crew for this board** privately in `CREW_HOME/forks` and writes one Haiku agent definition per fork (`internal-tools-wren`), and a fork signs in under that name (`crew internal-tools-wren mcp get_board`). `loadCreds()` adds every fork as a person; a file that is not a forks file is refused. See `crew/CHANGELOG.md`
- **Fixed: `/api/help` answered 500 without a session.** It was not on the protected-prefix list, so no session was attached. It answers 401 now

- **`get_task` reads less by default.** A plain read gives the 5 newest updates, newest first, so a long thread no longer fills an agent's context. A read with `since` or `prefix` still gives every match oldest first, so catching up from the newest update you have (`"since": "<update id>"`) never skips one. `limit` and `order` override both defaults. The tool description, the agent skill and the crew documents say how to read a whole thread and how to catch up; the PM finds its question with `prefix: "QUESTION:"`, and Boss finds a `WAKE` comment with `prefix: "WAKE"`

- **Pinned boards.** Pin a board from its menu in the sidebar (**Pin to sidebar**, also on a customer's board) and it shows under **Pinned** in every workspace, with the team it belongs to. Clicking it switches to that workspace and opens the board. A pin is yours alone; a board you can no longer open, or that is archived, drops off the list. New `board_pins` table, and `GET`/`POST /api/pins`, `DELETE /api/pins/:projectId`
- **The inbox opens an item in place.** A task notification opens the task panel over the inbox, where you can read the task and comment as on the board. A message or a reply opens its conversation with the reply box ready. When the board is in another workspace, the inbox switches there first. Notifications for messages now keep the conversation they belong to (`notifications.message_id`), so mail and push links open that conversation too (`?view=messages&message=<id>`); older ones open the board's messages
- `GET /api/projects/:id/workspace` says which workspace opens a board for the caller: its team, or the personal workspace for a customer contact

- **New crew** on the Crews page is a five-step wizard that anyone can follow. It makes the crew from the instance admin's session, so no `crews:manage` key or window is needed (`POST /api/admin/crews`, written to the agent audit as the Crews page).

  - Each crew gets a home folder of its own, `~/crew-home/<slug>`, so several crews can share one computer.
  - The crew starts in one of two ways: one message pasted into the Claude Code session you already work in, which then acts as Boss next to its own work, or a new window that is only Boss, with `CREW_HOME` set and both crew folders added. The page names the option to pick on each start-up question: the folder-trust screen and the MCP screen both start on the option you do not want.
